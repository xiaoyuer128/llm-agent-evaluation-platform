# 06 测试计划与测试用例

状态 **设计基线 v0.2**。所有应用用例处于待开发状态。测试编号只分配给一个主验收阶段，后续可复跑。

## 策略与数据

- 单元覆盖状态转换、请求去重、评分器、指标计算与错误映射。使用固定时钟、随机源和独立期望数据。
- API 契约覆盖 FastAPI 请求校验、HTTP 状态与权限。HTTPX stub 模拟限流、延迟、超时、结构化输出和畸形响应。
- 管理台使用 API 契约样例验证状态和空值展示，浏览器端到端测试覆盖导入、发布、提交、轮询和查看结果。
- M1 集成使用 PostgreSQL，M2 起加入 Redis、独立 Linux Celery Worker 和 Dispatcher。验证真实事务、锁、消息重投和 Worker 中断。Celery eager 测试仅覆盖进程内逻辑。
- 回归夹具包含规则答案、中文开放问答、两个确定性 Agent 工具、金标轨迹和人工结论，数据使用合成或经审批脱敏的内容。
- 基础设施验证用临时数据库、唯一测试队列及服务隔离。异步断言使用截止时间轮询；失败保留请求 ID、运行/执行项 ID、迁移版本、脱敏日志和 JUnit 报告。

## Worker 并发压测

1. **建立基线。** 固定数据集、候选和裁判配置、请求额度、CPU/内存配额和样本数量。逐档调整 Celery prefork 的进程数，区分使用固定延迟的网络替身与经批准的真实供应商两组数据。
2. **定位瓶颈。** 分别采集排队、领项与写回事务、候选请求、裁判请求、限流等待及重试退避时长；同时采集每分钟终结项数、端到端 P95、Worker CPU/内存、连接池等待和 429 比例。根据执行项的阶段耗时及资源占用判断模型 I/O 是否占主导。供应商或数据库已饱和时，先按对应瓶颈处理。
3. **验证单进程并发。** 模型 I/O 主导且额度有余量时才开启 `asyncio` 试验。在相同机器和全局并发请求预算下比较吞吐、P95 和失败率，记录各进程实际在途请求数。复跑 T05–T08、T10 和 T27，确认超时、取消、重投、租约恢复和候选工件复用均可对账。结果进入性能报告，达到验收后再改变 Worker 默认配置。

## 发布门禁

M1 起 CI 运行 lint、单元、契约和基础设施集成测试，验收关联功能时启用对应场景。各阶段通过本阶段关联用例后交付。进入预发前全部适用的 P0 用例须通过，T18 属于 M6 P1。数据库迁移及恢复演练有记录。首轮建议核心状态与评分模块分支覆盖率 ≥ 85%，与全仓覆盖率分开报告。真实裁判和供应商验收在隔离环境按审批额度执行，固定样本、模型、并发和版本。性能报告记录机器规格、样本规模、预热、分位数方法、失败率和提交 SHA；fake 压测与真实供应商端到端结果分别报告。

计划命令随 M1 落地为 `uv run --locked pytest -m "not integration and not live"` 与 `uv run --locked pytest -m integration`。live 用例通过显式开关启用。
